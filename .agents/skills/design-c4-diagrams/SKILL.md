# Проектирование C4-диаграмм

Здесь — правила нотации C4 и конвенции проекта.
Рендер, валидация и ловушки Mermaid — в скилле `design-mermaid-diagrams`.

## Процесс

- Перед каждой диаграммой задай уточняющие вопросы (гранулярность, соседние элементы, детализация, формат подачи)
- После создания диаграммы сделай паузу для ревью человеком.

## Стиль диаграмм

Диаграммы должны быть пригодны для слайдов 16:10 и проектора, поэтому нужен минимализм:

- короткие имена («Пользователь», не «Пользователь мессенджера»);
- однострочные короткие описания;
- все надписи на диаграмме лаконичные, подробности — под диаграммой;
- в содержании диаграмм очевидный контекст не дублировать.

Подробности (маршруты, лимиты, порты) можно разместить таблицей или списком под диаграммой.

## Диаграмма C4 Context

- `Person` для пользователей
- `System` для систем
- `System_Ext` для внешних систем
- серый цвет различает внешние/внутренние.
- `System_Boundary` при единственной системе избыточна.

## Диаграмма C4 Container

- `Container` для модулей
- `ContainerDb` для хранилища (включая in-memory)
- строить схему, валидную для prod, а не dev окружения
- маршруты API на связях не размещаются

## Диаграмма C4 Component

- `Container_Boundary` рассматриваемого контейнера; внутри — `Component`; рядом — соседние контейнеры (кто вызывает, где данные).
- Компоненты по ответственности, не по файлам
- DTO отдельными компонентами не выделять.

## Диаграмма C4 Code

Для отображения структуры кода:

- Тип `classDiagram`
- Описывать публичный контракт, без деталей реализации, без приватных полей.
- Применять `direction LR`, чтобы лучше помещалось на слайде

Для отображения сценариев использования:

- Тип `sequenceDiagram`
- один сценарий = один файл
