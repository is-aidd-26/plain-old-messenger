# SRS — Plain Old Messenger

Спецификация требований к реализации. Продуктовый контекст, цели и пользовательские сценарии — в [PRD.md](PRD.md).

## 1. Введение

Документ предназначен для разработчиков (студентов и преподавателей курса). Он фиксирует функциональные требования, требования к внешним интерфейсам и ограничения реализации. Документ не описывает внутреннее устройство кода — это решения разработчика.

## 2. Общее описание системы

Система состоит из двух компонентов:

- **Бэкенд** — REST API на ASP.NET Core (.NET 10, C#). Хранит данные и обслуживает запросы фронтенда.
- **Фронтенд** — SPA на React 19 + TypeScript, сборщик Vite. Общается с бэкендом по HTTP (JSON).

Пользователь работает только с фронтендом; бэкенд напрямую не доступен для конечного пользователя.

## 3. Функциональные требования

Приоритеты: **Must** — обязательно, **Should** — желательно.

| # | Требование | Приоритет |
| --- | --- | --- |
| F1 | Пользователь входит в приложение, указав только никнейм (уникальность в рамках сессии не проверяется) | Must |
| F2 | Ведётся список диалогов пользователя; новый диалог начинается с указания никнейма собеседника | Must |
| F3 | В личном диалоге 1-на-1 пользователь отправляет текстовое сообщение | Must |
| F4 | Пустое сообщение (пробелы или отсутствие текста) отклоняется с понятной ошибкой | Must |
| F5 | Пользователь читает историю диалога; каждое сообщение содержит никнейм автора, текст и время отправки | Must |
| F6 | Новые сообщения появляются в открытом диалоге без перезагрузки страницы (опрос сервера) | Must |
| F7 | Длина сообщения ограничена лимитом в 500 символов | Should |
| F8 | Диалог с самим собой разрешён и работает как обычный диалог (сценарий: две вкладки одного браузера) | Must |

## 4. Требования к внешним интерфейсам

API бэкенда должен предоставлять операции:

- отправка сообщения указанному собеседнику;
- получение списка диалогов пользователя;
- получение истории указанного диалога;
- получение новых сообщений диалога (для поллинга).

Точные состав ресурсов и маршруты — на усмотрение разработчика. Обмен данными — JSON поверх HTTP; отдельные сообщения об ошибках валидации возвращаются с кодом 400 и текстом ошибки.

## 5. Ограничения реализации

- **Хранение в памяти процесса (на текущем этапе):** данные (пользовательские сессии, диалоги, сообщения) живут в памяти сервера; после перезапуска сбрасываются. Постоянное хранение истории — в планах развития (PRD, раздел «Будет реализовано позднее»).
- **Обновление в реальном времени** — периодический опрос (polling) REST API со стороны фронтенда с интервалом порядка секунд. WebSocket, SSE и прочие push-механизмы не используются.
- **Технологический стек фиксирован:** ASP.NET Core (.NET 10, C#) для бэкенда, React + Vite + TypeScript для фронтенда. Сторонние библиотеки — только при действительной необходимости.
- **Без over-engineering:** без слоёв абстракций «на вырост», без конфигурации окружений сверх необходимого, без библиотек, без которых можно обойтись.

## 6. Нефункциональные требования

| # | Требование |
| --- | --- |
| N1 | Код бэкенда собирается `dotnet build` без предупреждений анализаторов |
| N2 | Код фронтенда проходит `npm run lint` и `npm run format:check` |
| N3 | Код умещается в уме: каждый файл читается за один присест, типичный файл — не более пары экранов |
| N4 | Проект запускается на компьютере студента с .NET 10 SDK и Node.js 20+ без дополнительных шагов, кроме описанных в README |
| N5 | README и документы в docs/ соответствуют текущему состоянию проекта и обновляются вместе с ним |

## 7. Принятые решения

- Лимит длины сообщения — 500 символов (F7).
- История диалога хранится в памяти целиком, без обрезки (объёмы учебные).
